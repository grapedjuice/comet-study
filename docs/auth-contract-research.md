# Authentication contract research (2026-09-22)

Scope: specification §§3.1 and 5, checked against current public Better Auth documentation. This is a **documentation/source-contract review**, not a tested local configuration, production deployment, email-provider call, or race test. The findings are a packet for the later authentication module; foundation acceptance remains a prerequisite.

## Decision

**Better Auth alone does not meet the specification as written.** Its magic-link plugin can satisfy short-lived, hashed, single-use verification when explicitly configured, and it has a PostgreSQL Drizzle adapter and Next.js handler. But its documented database [`session.token` is the same token used in the cookie](https://better-auth.com/docs/concepts/session-management); the spec requires a **secure token hash** in `sessions_auth`. I found no documented setting that hashes the stored session token while preserving Better Auth's session lookup. Do not silently relabel the plaintext `token` column as a hash or modify Better Auth internals. Either use a narrowly scoped auth implementation whose session storage is hashed, or explicitly revise that requirement after security review before selecting Better Auth. The spec's exact `/api/v1/auth/*` routes and JSON envelopes also need an app-owned contract layer; Better Auth's native API is different. This conclusion is an inference from the cited public contract, not proof that no undocumented extension exists.

## Supported pieces and configuration constraints

| Magic link | [Plugin](https://better-auth.com/docs/plugins/magic-link) exposes `POST /sign-in/magic-link` and `GET /magic-link/verify`, defaults to five-minute expiry, and automatically signs up new users unless `disableSignUp` is set. Its `storeToken` defaults to `"plain"`, but supports `"hashed"` or a custom hasher. | Set `storeToken: "hashed"` explicitly. The request sends proof to an email address; a valid redeemed link proves mailbox control. Do not enable another sign-in path that bypasses domain/verification checks. |
| One-time redemption | The [plugin documentation](https://better-auth.com/docs/plugins/magic-link) says each attempt atomically consumes the token; retries fail with `INVALID_TOKEN`. If verification uses secondary storage, `getAndDelete` is required; separate get/delete is disallowed. | Prefer database-backed verification with the Drizzle adapter. Still run a two-request concurrency test against the chosen package version and PostgreSQL before asserting the acceptance check. Do not substitute a secondary store lacking atomic consumption. |
| Drizzle/PostgreSQL | The [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle) supports `provider: "pg"` and CLI schema generation followed by Drizzle migrations. Expiry refresh is not evidence of session-token rotation. The stricter rotation requirement needs a verified implementation or a documented spec decision. Avoid cookie-cache/stateless/secondary-storage options until revocation and hashed-storage requirements are resolved. |
| Next.js and cookies | [Next integration](https://better-auth.com/docs/integrations/next) mounts `GET` and `POST` at `/api/auth/[...all]` using `toNextJsHandler(auth)`. Do not disable CSRF/origin checks. Server mutations must resolve and recheck the session and app account status. The configured base path can move native routes but does not rename endpoint methods or produce spec envelopes. |

Server-side `auth.api` calls may need separate limits; verify in the selected version. |

## Exact-domain and route boundaries

The app must parse and lowercase the email, then require the domain after the single `@` to equal `utdallas.edu` exactly; `student@utdallas.edu.attacker.test` and `student@sub.utdallas.edu` do not qualify. Better Auth's [request hooks](https://better-auth.com/docs/concepts/hooks) support prevalidation, but the documented example uses an `endsWith` test for a different domain. That example does **not** establish the spec's exact-domain rule. Apply the same gate before link issuance, before user creation/session issuance, and on every protected read/mutation; account-email changes and any future OAuth path must preserve it. A verified provider email claim would need to be checked if sanctioned UTD SSO is later configured. Until then, a magic link is verified-email fallback, not university SSO. Treat email existence and ineligible-domain responses with the spec's enumeration policy in mind.

The specified `POST /api/v1/auth/request-verification` and `POST /api/v1/auth/verify-email` (token in JSON body), plus `POST /api/v1/auth/sign-out`, require exact app responses and the `/api/v1` success/error envelopes. Better Auth's [magic-link routes](https://better-auth.com/docs/plugins/magic-link) instead use `POST /api/auth/sign-in/magic-link` and `GET /api/auth/magic-link/verify?token=...` at the default base path; the [Next handler](https://better-auth.com/docs/integrations/next) exposes those under `/api/auth/[...all]`. An app-owned facade can translate request/response shape only if it preserves Better Auth's cookies and atomic consume semantics; a hand-written token consume alongside the plugin would invalidate the guarantee. `GET /api/v1/me`, profile updates, export, and deletion are application contracts beyond the native magic-link endpoints. Callback URLs must be constrained to trusted local destinations to preserve a safe return URL.

## Open verification before implementation acceptance

Pin a Better Auth release and check the installed package against this note, especially session storage hooks, token rotation, atomic PostgreSQL consume under simultaneous redemption, normalization behavior, user `emailVerified` transition, response enumeration behavior, and cookie attributes. The public docs do not establish compliance with the spec's session-token hash, `email_verified_at`, `used_at`, exact routes/envelopes, or exact-domain rule by default. No secrets or live provider calls were used for this review.
