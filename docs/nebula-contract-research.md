# Nebula API contract research (2026-09-22)

This is a **source-code contract inspection**, not a live production response check. I inspected the public [UTDNebula/nebula-api repository](https://github.com/UTDNebula/nebula-api) at commit [`8e2e67e8671aa5859205b154ffb3f20ef5879cb6`](https://github.com/UTDNebula/nebula-api/tree/8e2e67e8671aa5859205b154ffb3f20ef5879cb6), especially its [generated Swagger 2.0 file](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/docs/swagger.yaml), [route registrations](https://github.com/UTDNebula/nebula-api/tree/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/routes), [response handler](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/controllers/controller_utils.go), and [schema](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/schema/objects.go). No API key was used; production deployment, data contents, quotas, headers, and error bodies remain unverified. The repository [README](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/README.md) points to production Swagger at `https://api.utdnebula.com/swagger/index.html` and says requests to `https://api.utdnebula.com` use an `x-api-key` header. The generated spec declares the same header security scheme.

## Routes and differences from the specification

All routes below are `GET`. Paths and response types are from [Swagger](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/docs/swagger.yaml) and corroborated by [registered routes](https://github.com/UTDNebula/nebula-api/tree/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/routes).

| Expected surface | Registered contract at this commit | Relevant response `data` / caveat |
| --- | --- | --- |
| `/course` | `/course`, `/course/{id}`, `/course/all`, `/course/sections`, `/course/{id}/sections`, `/course/professors`, `/course/{id}/professors` | Search returns `Course[]`; by ID returns `Course`. A course has `_id`, `subject_prefix`, `course_number`, `title`, `catalog_year`, and section ID references. `/course/all` is unpaginated. |
| `/section` | `/section`, `/section/{id}`, `/section/courses`, `/section/{id}/course`, `/section/professors`, `/section/{id}/professors` | Search returns `Section[]`; by ID returns `Section`. Section has `_id`, `course_reference`, `academic_session`, `section_number`, professor ID references, `instruction_mode`, `meetings`, and `grade_distribution`. Meeting has dates, days, times, modality, building, and room. Capacity and enrollment status are **not** explicit fields in this schema. |
| `/professor` | `/professor`, `/professor/{id}`, `/professor/all`, `/professor/courses`, `/professor/{id}/courses`, `/professor/sections`, `/professor/{id}/sections` | Search returns `Professor[]`; related routes return courses or sections. Professor has `_id`, names, titles, office, office hours, and section IDs. |
| `/grades` | No bare `GET /grades`. `/grades/overall`, `/grades/semester`, `/grades/semester/sectionType`, plus `/course/{id}/grades`, `/section/{id}/grades`, `/professor/{id}/grades`. | Overall/resource routes return integer grade-distribution arrays; semester variants return grade distribution records. These are aggregate/course-section-professor data, not individual student grades. |
| `/rooms` | `/rooms` | Unpaginated `BuildingRooms[]`: `building`, `lat`, `lng`, `rooms[]` with `room` and `capacity`. No documented room query filters, equipment, accessibility, or live free/busy field. |
| `/events` | No bare `GET /events`. `/events/{date}`, `/events/{date}/{building}`, `/events/{date}/{building}/{room}`, `/events/{date}/{building}/{room}/sections` | `date` is an ISO date path parameter. Date route returns `MultiBuildingEvents<SectionWithTime>`: `date → buildings[] → rooms[] → events[]`; each event has a section ID and start/end time. This represents scheduled class meetings. |
| `/calendar` | No bare `GET /calendar`. `/calendar/{date}`, `/calendar/{date}/{building}`, `/calendar/{date}/{building}/{room}` | Same date/building/room hierarchy, with `Event` objects containing summary, start/end time, location, etc. This is **Comet Calendar event data**, not term metadata. |

For room occupancy, the source also registers date/building/room variants under [`/astra`](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/routes/astra.go) and [`/mazevo`](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/routes/mazevo.go). Thus `/events` alone does not evidence the complete CourseBook + Ad Astra + Mazevo occupancy pipeline assumed by specification §3.7. The actual completeness/freshness of each production feed is unknown.

## Filters, pagination, response, and errors

- `/course`, `/section`, `/professor` accept `offset` for pagination. The server uses a configurable `LIMIT`, default **20** in [environment configuration](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/configs/env.go); the [pagination helper](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/configs/setup.go) skips that offset and applies the limit. Related search routes use `former_offset` and `latter_offset`. The response has no total, next cursor, or next-page link; a client must stop on a short/empty page, while guarding against inconsistent upstream ordering. No explicit sort is configured in the basic search helper.
- Documented `/course` filters include `course_number`, `subject_prefix`, `title`, `description`, `school`, `credit_hours`, `class_level`, `activity_type`, and others. `/section` includes `section_number`, `academic_session.name`, `instruction_mode`, `meetings.meeting_days`, `meetings.start_time`, `meetings.location.building`, and `meetings.location.room`. `/professor` includes `first_name`, `last_name`, `email`, `office.building`, and office-hour fields. The complete parameter lists are in [Swagger](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/docs/swagger.yaml). The [filter implementation](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/schema/filter.go) validates queryable schema fields, takes the first supplied value, and builds a BSON equality filter. No general fuzzy/full-text search contract is established by these routes.
- Grade aggregate filters are `prefix`, `number`, `first_name`, `last_name`, `section_number` in [Swagger](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/docs/swagger.yaml). `/rooms`, `/events/{date}…`, and `/calendar/{date}…` have no documented query filters or pagination.
- The documented common JSON envelope is `{ "status": number, "message": string, "data": T }`; error endpoints declare the same envelope with string `data`. The [handler](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/controllers/controller_utils.go) emits HTTP status in `status`, uses `"success"` on successful paths and `"error"` or a more specific message on failures. Swagger documents 400 and 500 for catalog search, 404 on several related/resource or location routes, and 500 on date routes. The handler currently puts raw internal error strings in `data` for 500s, so clients should not expose upstream text to users. Swagger status listings are incomplete relative to some handlers (for example course-by-ID handles 404); treat each response status defensively.

## Rate and production policy boundary

The checked-in [Swagger gateway extension](https://github.com/UTDNebula/nebula-api/blob/8e2e67e8671aa5859205b154ffb3f20ef5879cb6/rest/docs/swagger.yaml) contains a `STANDARD: 1000` read-request quota per minute per project, but its title and Google backend identify a **developer** API configuration. I found no verified public production rate limit, `429`/`Retry-After` contract, caching policy, or permitted sync cadence. Treat those as **unknown**, request policy from Nebula before scheduling room/event polling, and honor any observed `429` and `Retry-After` conservatively. No live authenticated call was made.

Implementation implication: keep the local specification's paths as product requirements, but implement an isolated client against the documented concrete routes and validate actual production responses with an authorized key before enabling live ingestion. Do not infer section capacity, room features, feed freshness, or term-calendar metadata from this source schema.
